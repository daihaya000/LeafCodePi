# 設定画面 全体レイアウト再考案

**状態:** 廃止済み（旧版）— 本ドキュメントが提案した「一般」タブ内カテゴリ分けは、
さらに「設定→一般メニューの廃止」により置き換えられた。現行実装は
`エンジン / モデル / エージェント / 拡張` の4トップレベルタブ構成であり、
本書の `#general-basic` 等のハッシュ形式は `#engine-basic` 等に統合された
（旧ハッシュはリダイレクトで吸収）。詳細は `SettingsView.tsx` を参照。
**対象:** `web/src/components/settings/SettingsView.tsx`
**目的:** 「一般」に集約された設定を役割ごとに分け、目的の設定へ短い導線で到達できるようにする。

## 1. 現状の課題

現在は `エンジン / モデル / 一般` の3タブ構成だが、「一般」だけが12パネルの長い一列になっている。

| 現在の状態 | 問題 |
| --- | --- |
| ブラウザ、通知、応答、エージェント、MCPなどを同じ列に配置 | 利用者向け設定と開発者向け設定の優先度が分からない |
| 各パネルが同じカードの強さで表示される | 重要度・技術的な難しさ・操作量の差が伝わらない |
| すべての一般パネルを同時にマウント | 初期表示時に不要な設定まで処理され、画面の責務も曖昧になる |
| 画面末尾の説明文で他タブへの導線を補っている | 情報設計ではなく注記で補完している |

## 2. 採用案

**トップレベルの3区分は維持し、「一般」だけに第2階層のナビゲーションを追加する。**

```text
設定
├─ エンジン
│  ├─ ランタイム状態・再起動
│  └─ ローカル LLM
├─ モデル
│  ├─ 認証
│  ├─ 利用するモデル
│  └─ 生成モデル
└─ 一般
   ├─ 基本                         ← 初期表示
   ├─ 応答
   ├─ エージェント環境
   └─ 拡張・連携
```

「一般」の中では1カテゴリだけを表示する。カテゴリを切り替えても入力途中の内容は破棄しない。

### 一般カテゴリと既存パネルの対応

| カテゴリ | 配置するパネル | 表示の扱い |
| --- | --- | --- |
| 基本 | ブラウザ、ナビゲーター、通知音 | 短い設定行を中心にまとめる。テーマは既存のサイドバー操作への案内を残す |
| 応答 | 思考要約の翻訳、コンテキスト圧縮、ハング判定 | 日常的な動作設定。説明を近接配置する |
| エージェント環境 | `AGENTS.md`、スキル、エージェント | エディター・一覧を使うため、横幅を広く確保する |
| 拡張・連携 | 拡張機能、MCPサーバー | 技術設定としてまとめ、パスや注意事項を各パネル内に閉じ込める |

概要ダッシュボードは追加しない。概要カードを増やすと、実際の設定までのクリック数と重複情報が増えるため、初期カテゴリを「基本」にする。

## 3. レイアウト

### デスクトップ

```text
┌──────────────────────────────────────────────────────────────┐
│ 設定                                                        │
│ [エンジン] [モデル] [一般]                                  │
├──────────────┬───────────────────────────────────────────────┤
│ 一般          │ 基本                                          │
│  基本         │ 表示・通知に関する設定                         │
│  応答         │ ┌───────────────────────────────────────────┐ │
│  エージェント │ │ ブラウザ                         [ toggle ] │ │
│  拡張・連携   │ │ メッセージ移動ボタン             [slider ] │ │
│               │ │ 通知音                         [select ] │ │
│               │ └───────────────────────────────────────────┘ │
│               │                                               │
│               │ 変更が大きい設定は別カードとして下に配置       │
└──────────────┴───────────────────────────────────────────────┘
```

- 既存のトップタブは残し、一般選択時だけ `12rem` 程度のカテゴリナビを表示する。
- コンテンツの最大幅は現在の `max-w-3xl` から、編集領域を確保できる `max-w-5xl` 相当へ広げる。
- カテゴリナビは `nav` として扱い、選択中は `aria-current="page"` とアクセントで示す。
- ページ全体を1つのスクロール領域にし、入れ子のスクロールを増やさない。
- 小さな設定は同一サーフェス内の行、大きなエディター・一覧は独立カードにする。12枚の同型カードを縦に並べない。

### モバイル

- `MobileMenuHeader` は現状のまま使用する。
- トップタブと一般カテゴリナビは横スクロール可能なタブ列にし、画面幅を押し広げない。
- カテゴリを選ぶとナビ列の下に1カテゴリを1列で表示する。
- コントロールのタップ領域は44pxを下限とし、説明文は操作対象の直下に置く。
- 長い `AGENTS.md` 編集や一覧は横方向に溢れず、本文だけがページ内で折り返す。

## 4. エンジン・モデルの整理

一般だけを分割するのではなく、トップレベルの表示順も利用手順に合わせる。

### エンジン

1. ランタイム状態と再起動
2. ローカル LLM の起動・停止
3. ローカル LLM の起動設定

現行の `HostRestartPanel`、ヘルス情報、`LlamaServerSettings` の責務は変更しない。状態確認と操作を画面上部に置き、詳細設定をその下に置く。

### モデル

1. プロバイダー認証
2. 利用するプロバイダー・モデル
3. 生成モデルとフォールバック

認証前にモデル一覧を探す状態を避けるため、`ProviderAuthPanel` を `ProviderModelsPanel` より前に配置する。API・保存仕様は変更しない。

## 5. 操作・状態の仕様

- 既存の保存タイミング、再読み込み、エラー表示、インストール中表示は変更しない。
- カテゴリ切替では現在のコンポーネントを `hidden` で保持し、編集中の内容を破棄しない。初期実装では読み込み処理を変えず、遅延マウントは別の性能課題として扱う。
- トップタブに加えて `generalSection` を持ち、カテゴリ選択を URL ハッシュへ反映する。
  - 例: `#general-basic`、`#general-response`
  - 直接リンクと再読み込みで同じカテゴリを開く。
- 非表示カテゴリは `hidden` で保持し、`AGENTS.md` の編集中テキストを失わない。
- 非表示要素がキーボードフォーカスや読み上げ対象にならないよう、HTML の `hidden` 属性を使う。ページ再読み込み時は、従来どおり保存済みの値を再取得する。
- 既存のコンポーネントは原則そのまま再利用し、`SettingsView` が表示カテゴリと順序を管理する。API route、設定ファイル、保存形式は追加しない。

## 6. デザイン契約

`C:\Users\Daichi\.pi\agent\DESIGN.md` のトークンと、既存のテーマ変数を使用する。

- ページ背景は `bg-bg`、設定面は `bg-surface`、補助面は `bg-surface-2`。
- テキスト階層は `text-text` / `text-muted` / `text-faint` で表現する。
- 境界は `border-border` のヘアラインを基本にし、濃い枠や強い影を増やさない。
- 選択状態、フォーカス、リンクは `accent` 系だけを使う。カテゴリごとに色を変えない。
- セクション間は `spacing.lg` 以上、行内は `spacing.sm`〜`spacing.md` を基準にする。
- ライト・ダーク・Oyster のテーマで同じ階層が保たれるよう、色の直書きは行わない。

## 7. アクセシビリティと状態表示

- トップレベルは `nav aria-label="設定"`、一般カテゴリは `nav aria-label="一般設定"` とする。
- 選択中のタブ・カテゴリは `aria-current` または `aria-pressed` で機械的にも判別できるようにする。
- 各カテゴリの見出しは1つにし、パネルの既存見出しとの階層を崩さない。
- 保存中・読み込み中・エラー・導入中の `role="status"` / `role="alert"` は維持する。
- 既存のアクセント色フォーカスリングを維持し、色だけで状態を表現しない。
- `prefers-reduced-motion` ではカテゴリ切替にアニメーションを追加しない。

## 8. 実装の切り分け

### Phase 1: 情報設計と表示切替

- `SettingsView.tsx` にトップタブ・一般カテゴリの定義を追加する。
- 一般をカテゴリごとの表示に変更する。
- 既存パネルのAPI通信・保存処理は変更しない。
- ハッシュによる直接リンクを追加する。

### Phase 2: 密度の調整

- 基本・応答カテゴリの短い設定を、行中心のレイアウトへ調整する。
- エージェント環境・拡張連携の編集領域は `max-w-5xl` の幅を活用する。
- エンジン・モデルの順序を利用手順に合わせる。

### Phase 3: 回帰確認

- `SettingsView.test.tsx` にカテゴリ切替、ハッシュ復元、非表示カテゴリのアクセシビリティを追加する。
- `npm --prefix web run typecheck`
- `npm --prefix web run lint`
- `npm --prefix web test`
- ライト / ダーク / Oyster、デスクトップ / モバイルで手動確認する。

## 9. 受け入れ条件

- 一般を開いた初期画面に12パネルを同時表示しない。
- 一般内の全設定へ、カテゴリ選択を含めて最大2操作で到達できる。
- カテゴリ切替で編集中の内容を破棄せず、ページ再読み込みでは保存済みの値を正しく再取得する。
- デスクトップではカテゴリナビと設定本文の役割が明確で、モバイルでは横スクロール以外の画面溢れがない。
- 既存の保存、再読込、エラー、認証、起動・停止、導入処理が従来どおり動く。
- `DESIGN.md` のトークン、アクセント1色、ライトファーストの階層に準拠する。
