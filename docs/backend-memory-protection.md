# Backendのヒープ枯渇対策

## 確認済みの障害と計測

2026-10-07 08:29:44 UTC、generation `b3f47932712c1a2c` のBackendが終了コード134で停止。stderrに `Reached heap limit Allocation failed - JavaScript heap out of memory` とGC後約4124 MiBが記録された。直接原因はV8ヒープ枯渇。4 GiB全体の保持元は未特定で、単一履歴だけがクラッシュ原因とは断定しない。

548 MiBの実セッション履歴の大部分はtool-result画像のbase64だった。実SDK 1.0.0で、通常読込の保持ヒープ565 MiBに対して軽量読込は44 MiB、コピーサイズは約27 MiB、読込は約5.2秒。現在の `buildSessionContext()` 全体のハッシュが通常読込と一致し、原本のサイズ・更新時刻も不変だった。これは個別計測で、全環境での性能保証ではない。

## 読込と履歴保全

- `backend/core/session-memory-guard.mjs` は64 MiB超の履歴を、1 MiBずつのJSONLスキャンで一時コピーへ軽量化する。SDK自体も分割読込するが全エントリーを保持するため、SDKへ渡す前の削減が必要。
- SDKと同じleaf/compaction保持範囲から現行コンテキストを判定する。**現行コンテキストの画像・テキストは変更しない。** 範囲外のtool-result画像を通知へ置換し、範囲外のtool textだけを25,000文字に制限する。
- 現行画像合計16 Mi文字超、一時コピー64 MiB超、1行16 MiB超、10万エントリー超は明示エラーで拒否。v3以外の巨大履歴も自動移行しない。現在必要な画像を黙って切り捨てない。
- スキャン前とSDK読込前にヒープ余裕を確認。上限25%または512 MiBを予備領域に取り、展開コストを読込サイズの8倍で見積もる。計算は保守的な目安であり、メモリ使用量の厳密な保証ではない。
- 原本は変更しない。読込前後のサイズ・inode・device・mtime/ctimeを照合し、変更時はHTTP 409。末尾改行がない大容量履歴は、後続追記のJSON結合事故を防ぐため改行修復を要求する。自動修復はしない。
- 一時コピーは権限0600で作成し、成功・失敗どちらでも削除する。書込先容量不足・途中書込・SDK失敗を握り潰さない。Windowsのアクセス制御は既存のユーザーTEMPディレクトリーに依存する。
- SDKの将来の追記は原本へ行う。実SDKで、追記前の原本全バイトが追記後も保持されることを検証している。
- SDK 1.0.0の保存内部構造に依存するため、保存状態が未対応なら拒否する。**軽量コピーの原本上書きと、省略済みエントリーを含む過去分岐・forkは変更前にHTTP 409で拒否する。** 省略内容を永続履歴として保存しない。大容量のsetSessionFile直接再読込も制限する。
- ToDoは巨大履歴/圧迫時に既存のディスクスキャナーへフォールバック。軽量化エラー・IOエラーを空履歴として表示しない。

## 新規tool-result画像

- テキスト制限は25,000文字（scan系8,000文字）のまま。
- 大きな画像はSDKの `resizeImage` で逐次再圧縮する。基本目標はbase64合計512 Ki文字、最大寸法1280×1280。複数画像では目標を分配するが1画像32 Ki文字以上とする。
- 画像数や内容は強制省略しない。再圧縮が失敗・無効・拡大の場合は原画像を保持する。したがって画像サイズは目標であり、厳密な上限ではない。拡張のdetails/isError等も保持する。
- ネイティブデコーダーを並列起動せず、ピークメモリの増幅を避ける。

## 圧迫時回収・反映・限界

30秒ごとに圧迫を確認し、再構築可能なキャッシュと1分以上触られていない安全な休止セッションを回収する。通常の休止基準は1時間。実行中・圧縮中・Goal Loop・承認/質問待ち・閲覧中・Bot・バックグラウンド作業所有セッションは回収しない。`[backend-memory] pressure` は最大1分に1回、数値カウンターのみを記録する。

変更は次回のランタイムビルド・起動で反映される。稼働中の作業を止めるため、自動再起動しない。

同期スキャンは大容量ファイルで数秒ブロックし得る。実行中の無制限割当、デコーダー失敗後の原画像累積、ネイティブメモリ枯渇を完全には防がない。過去画像のオンデマンド復元・完全なfork対応は今後の課題で、現在は履歴保全を優先して安全に拒否する。再発時はログ・圧迫カウンターと、停止可能な検証環境でのヒープ保持元を調査する。
