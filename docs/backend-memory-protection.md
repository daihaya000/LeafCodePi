# Backendのヒープ枯渇対策

## 確認済みの障害

2026-10-07 08:29:44 UTC、generation `b3f47932712c1a2c` のBackendが終了コード134で停止。`host.log` のstderrに `Reached heap limit Allocation failed - JavaScript heap out of memory` とGC後約4124 MiBのヒープ使用量が記録された。直接原因はV8ヒープ枯渇。どのオブジェクトが保持され続けたかは未特定で、巨大履歴だけが今回の原因と断定はしない。

## 防護

- `backend/core/session-memory-guard.mjs` でSDKが履歴を全件保持する前に、大容量履歴をJSONLストリーミングで一時的に軽量化する。ライブ作成・オフライン履歴表示の双方が対象。
- 一時コピーでは現在のsession tree leafから到達可能な古いtool-result画像を省き、直近の画像は合計16 MiBまで残す。各tool resultのテキストも25,000文字までに抑える。SDKへの読込が成功してからも、将来の追記は原本JSONLに行う。一時コピーは破棄し、原本は変更しない。
- 一時コピーが64 MiBを超える場合、1行16 MiB超、読込中に元ファイルが変わった場合は拒否する。大容量の旧形式（v3以前）はID/親子関係の変換と書戻しを安全に分離できないため拒否する。
- 一時コピーの8倍を展開コストとして見積もり、ヒープ上限の25%または512 MiBの大きい方を残せなければHTTP 503 / `SESSION_MEMORY_PRESSURE`。これは保守的な見積もりで、実際の最大使用量の保証ではない。
- ToDo一覧はサイズ/圧迫時に既存のディスクスキャナーへフォールバックする。履歴表示の拒否は空履歴に見せずエラーとして返す。
- 新しく保存するtool resultはテキスト25,000文字、画像base64合計512 KiB/呼出しまで。超過画像はモデルに渡す前に省略通知へ置換する。大きな画像を含むtool resultは再実行・細分化する。
- 30秒ごとにヒープ圧迫を確認し、再構築可能な履歴キャッシュと1分以上触られていない安全な休止セッションを回収する。通常の休止回収基準は1時間のまま。
- ストリーミング・圧縮・プロンプト実行中、Goal Loop、承認・質問待ち、閲覧中、Bot、バックグラウンド作業所有セッションは回収対象外。サブエージェントのファイルパス識別子も照合し、長いパスによるprovider登録失敗は固定長ハッシュ名で防ぐ。
- 圧迫中は `[backend-memory] pressure` を最大1分に1回記録。ヒープ使用量・上限・RSS・external・arrayBuffers・liveセッション数・キャッシュ数のみで、会話本文・認証情報・パスは記録しない。

## 適用と限界

変更は次のBackendランタイムビルド・起動で反映される。稼働セッションを止めるため、作業中に自動再起動しない。

旧履歴の画像データは実行中のメモリ上だけで省略され、元ファイルは保全される。以前のブランチへ切り替えると画像がない表示になることがある。大容量セッションの分岐先にも省略内容が引き継がれる。

この防護は巨大tool結果の再保持と履歴読込コストを制限するもの。実行中セッションや拡張の無制限な割り当て、ネイティブメモリ枯渇を完全には防がない。再発時は `host.log` のstderrと圧迫カウンターを比較し、停止可能な検証環境で保持元を調査する。上限増量や定期強制再起動を根本解決とは扱わない。
