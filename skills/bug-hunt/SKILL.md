# Bug Hunt

バグが明確に示されていない場合はまず探索し、不具合を再現し、原因を証明し、最小の修正と回帰テストで再発を防ぐ。
推測ではなく、実行結果・ログ・コード・履歴を根拠に判断する。

## 原則
- 最初に `AGENTS.md`、README、テスト設定、実行スクリプトを確認。プロジェクト固有の規則をこのスキルの一般則より優先。
- ユーザー・他エージェントの未コミット変更は保持。無関係な変更を修正・整形・revertしない。
- 常駐プロセス・破壊的Git操作・本番データ操作・外部送信は明示許可なしに行わない。
- 3段階以上の調査は `todowrite` で「再現/原因/修正/回帰/検証」を追跡。

## 完了条件
満たすまで「修正済み」と断定しない。
1. 期待値と実際値が明確
2. 不具合を再現した、または再現不能の理由と代替証拠がある
3. 根本原因をコード上の因果関係として説明できる
4. 修正が原因へ作用することを説明できる
5. 回帰テスト・自動検証・手動検証のいずれかが成功
6. 型検査・lint・テストが成功、または未実施理由を報告

## 1. トリアージ
バグが明確に示されていない（「動かない」「壊れた」など）場合は、まず何が起きているのかを探索する。エラーメッセージ・ログ・コードから症状を特定し、再現可能な具体的な不具合に落とし込む。
報告から抽出: 期待動作 / 実際動作 / 最小入力と手順 / 頻度と初回時期 / 環境とバージョン / エラーとスタック / 直前の変更と影響範囲。
コード・ログ・テスト・履歴から得られる情報は先に自分で調べる。調査を実際に妨げる不足情報のみ、`question` で一度に聞く。

## 2. 再現
安価で決定的な方法を優先: 既存の失敗テスト → 既存テストへの最小ケース追加 → 一回で終了する再現スクリプト/API → 手動操作。
実行コマンド・入力・環境・出力を記録。一時ログ・アサーションは最終差分に残さない。
再現できても盲目的に修正しない。スタックトレース・型/境界の証明・既知の競合など十分な代替証拠があれば進めてよい（制約を報告に明記）。

## 3. 調査
証拠をたどる:
- エラー文字列と関連シンボルを `grep`
- 失敗地点だけでなく、悪い値が生成された地点まで呼び出し元とデータフローを追う
- 最後の正常状態と最初の異常状態の境界を探す
- 回帰なら `git log -p -- <path>` / `git blame` / 非対話 `git bisect`
- 依存が候補ならロックファイル・変更履歴・公式仕様を確認

証拠表を維持する（一度に検証する仮説は一つ、反証された仮説を無言で使い続けない）:

| 仮説 | 根拠 | 反証方法 | 結果 |
| --- | --- | --- | --- |
| 初期化順序が逆 | `cwd` 未設定のスタック | 呼び出し直前を記録 | 確認済み |

バグ種別の観点:
- 状態・UI: stale state / 非同期順序 / mount-unmount / キャッシュキー / 空・loading・error
- 並行・flaky: 共有状態 / 時刻依存 / 乱数 / 未await / race / タイマー / リトライによる隠蔽
- 性能: 推測で最適化せず、同条件で修正前後に時間・回数・メモリを計測
- 境界値: null / 空 / 0 / 最大値 / Unicode / パス / タイムゾーン / 権限 / 切断
- 互換性: 公開API / 永続化形式 / 設定 / 依存バージョン / 旧データの利用有無

## 4. 根本原因
編集前に一文で因果関係を書く。
> `parseConfig` が `cwd` 設定前に呼ばれ、`resolve(undefined)` が例外を投げる。

「この行で落ちる」は失敗地点であり根本原因とは限らない。修正箇所は不変条件を所有する層（生成元 / 境界検証 / 利用側）に置く。
原因を絞れないまま複数変更を重ねない。仮説を3つ反証しても進展しなければ、追加ログ・最小再現・環境アクセスを依頼。

## 5. 修正
- 根本原因に作用する最小の変更
- 既存の設計・型・エラー処理・テスト方式に合わせる
- コメントはコードから読み取れない不変条件・理由がある場合だけ
- 公開API・永続化形式を変える場合、既存利用を確認し破壊的変更なら先にユーザーへ判断を求める

## 6. 回帰テスト
- 再現ケースを恒久テストにする（修正前で失敗し修正後で成功）
- 修正前実行を記録済みなら作業ツリーを巻き戻さない
- 不具合を生んだ境界条件を直接検証
- 実装詳細ではなく外部から観測できる契約を検証
- flaky は単なるリトライで解決せず決定性を回復
- テスト基盤がない/自動化コストが不釣り合いなら勝手に追加せず、再現可能な手動手順を残し制約を報告

## 7. 検証
プロジェクト定義のコマンドで、この順で確認:
1. 新しい回帰テストまたは最小再現
2. 変更モジュールの関連テスト
3. 型検査とlint
4. 影響範囲に応じた全体テスト
5. 必要な場合のみ元の操作による手動確認

性能・flakyの修正は複数回実行し修正前と同条件で比較。原因なら直し、無関係/環境要因なら根拠とともに分離して報告。

## 8. 報告
- **根本原因**: 因果関係と `path:line`
- **修正**: 変更内容と、その場所が適切な理由
- **回帰防止**: テスト名または手動検証手順
- **検証結果**: 実行コマンドと成否
- **制約・残存リスク**: 再現不能 / 未実施検証 / 意図的に触らなかった関連事項

根本原因が未確定なら「修正済み」ではなく「調査結果」または「暫定対策」と明示。

## 禁止する進め方
- 証拠なしに複数箇所を変更するショットガンデバッグ
- 失敗を隠すだけの例外握りつぶし・無制限リトライ・過度なデフォルト・fallback
- テストの期待値を実装に合わせて弱める
- 無関係な整形・リファクタ・命名変更を同じ差分に混ぜる
- 実行していない検証を成功扱い
- ユーザーの変更を退避・削除・revertして再現環境を作る
