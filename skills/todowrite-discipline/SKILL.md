# ToDo discipline — 起票に値する作業の todowrite

`todowrite` は起票に値する作業で必須。質問回答・説明・単発の小さな作業・制御toolだけの利用には強制しない。同じタスクでこのスキルを各ステップごとに再読込しない。

`todowrite` の ToDo はセッション単位で永続化される。前の会話で `pending` / `in_progress` のまま放置された ToDo は、セッション再開時にそのまま表示され続ける。これを放置しない。

## 起票に値するか

- **起票する**: 完了までに複数の依存する手順を要する作業。コード・ファイル・設定の変更、副作用のあるコマンド、検証、コミット、委譲を含むもの。複数フェーズの調査・不具合対応も含む。
- **起票しない**: 質問への回答・説明・単発の調査・相談・判定、単発の小さな作業（誤字1件の修正、状態・日時の確認など）。
- 迷えば起票する。「OK」「続けて」など前の会話の続きは、続けるタスクの規模で判断する。
- 起票しないと判断しても、実行ゲートに停止されたら `todowrite` で起票して再実行する。起票しない小さな変更でも、差分確認・関連検証・コミット確認は省かない。

## 規則

0. **会話冒頭の掃除（前会話 ToDo の残置禁止）**: 会話開始・再開時に前の会話由来の ToDo（`pending` / `in_progress`）が残っていたら、**新タスクの ToDo を作る前に**全項目を実態に合わせて `completed` または `cancelled` にリセットする。前会話の項目を新しいタスクに混ぜて引き継がない。本当に継続が必要な項目のみ、内容を明示して新規 ToDo として定義し直す。
1. **タスク開始時（最初の実作業）**: 起票に値するタスクで変更・shell・委譲・memory変更・未分類toolを使う場合は、最初の非制御toolより先に `todowrite` を実行し、non-empty list の現在項目を `in_progress` にする。`git status` / `git diff` も shell なので ToDo登録より前に実行しない。ToDo要求は最初の実質tool前、起票に値するread-only作業はポリシー確認と制御toolを除く3回目の実質読み取り前に登録する。起票不要な作業（質問回答・説明・単発の小さな作業）は免除。既存の `jev_judge` を明示的に使う単発判定もこの免除に含む。
2. **着手直前**: 対象ステップを `in_progress` にする。`in_progress` は常に 1 つだけ。起票した変更タスクでは、最終的な検証・コミット・Pushなどの完了工程より前に、独立した「レビュー・問題修正」ToDoを置く。変更内容・要件・関連テストをレビューし、問題があれば修正して関連検証と再レビューを繰り返す。問題がなければ修正は不要だが、レビュー工程自体は省かない。起票しない小さな変更も、コミット前に差分と関連検証を確認する。
3. **完了直後**: その場で `completed` にする。まとめて後回しにしない。
4. **完了宣言より先に ToDo 更新**: 実装・検証・報告のいずれかを「完了」と宣言する前に、対応する ToDo を必ず `completed` にする（順序を逆にしない）。
5. **コミット直前**: そのコミットに含まれる作業のToDoをすべて `completed` にしてからコミットする。コミットのトピック数 ≒ ToDo項目数が正常形。
6. **ターン終了時**: `pending` / `in_progress` を残さない。残る場合は理由と次の一手を報告し、`cancelled` にするか継続ToDoとして明示する。**次の会話に未完了 ToDo を持ち越さない** —— 持ち越す必要性が生じた時点で、その場で内容を `cancelled` にし、引き継ぎ先（次会話の冒頭で作る新規 ToDo やユーザーへの申し送り事項）を本文に明記する。
7. **ToDoを登録したタスクの最終報告**: 必ず `作業状況: 完了N件 / 未完了N件` の 1 行で開始する。ToDo未登録のタスク（短い質問回答・相談・判定・起票不要の単発作業）にはこの形式を使わず、結論を直接返す（変更した場合は変更内容と検証・コミット結果を含める）。`cancelled` は未完了に数え、未完了があれば各項目の理由と次の一手を同じ行か直後に書く。完了項目の再列挙は不要。次の行に**変更内容と成果**を具体的に書き、必要な検証結果やコミット/Pushの成否を続ける。件数だけで結果報告を終えない。

   例: `作業状況: 完了2件 / 未完了0件` → `docs/README.md にセットアップ手順を追記。リンクを確認し、コミット・Push済み。`
   中止例: `作業状況: 完了1件 / 未完了1件（Push中止: 認証失敗。次: 認証を復旧して再実行）` → `docs/README.md にセットアップ手順を追記し、リンク確認済み。ローカルコミット済み・リモート未反映。`

## 実行ゲートの条件

| 操作 | ToDo未登録時 |
| --- | --- |
| 制御tool、`show_image` / `show_video` / `show_audio`、`jev_judge`、`AGENTS.md` / `SKILL.md` のread、`skill_manage(action=view)` | 通過・読み取り回数に含めない |
| read / grep / find / ls / Web検索・取得 | 2回まで通過、3回目から停止 |
| 変更・shell・委譲・memory変更・その他の未分類tool | 初回から停止 |

- プロンプト内の`todo`等の単語で機械的に条件を厳しくしない。明示的なToDo管理依頼の対応順序は規則1で扱う。
- 未起票時の変更・shell・委譲・未分類toolは、Native SDKのモデル宣言から非公開にする（登録・権限は保持）。WebUIでは`tool_search`・`codemode`の発見・実行カタログも連動する。2回の読み取り後は読み取り宣言も隠す。必要なツールが見えなければ、先に`todowrite`を単独で呼び、次の呼び出しから作業する。質問・説明だけなら起票不要。
- `todowrite`はモデルから直接呼ぶ。`codemode`の中からは呼べない（ネストした結果はSDK/UIの復元用スナップショットにならないため）。
- 有効な`in_progress`項目を実際に登録した時点で、そのタスクのゲートを開く。登録前の同一バッチ操作、空・不正なリストでは開かない。開いた後も変更系は`in_progress`が1件ある間だけ通り、全項目`completed`・空リストでは再び停止する（read-onlyと、`cd`付きを含む`git status/diff/log/add/commit/push/fetch/merge`のコミット・確認工程は通過）。`memory_add`・`skill_manage`などの永続化は、最後の項目を`completed`にする前に行う。完了後に必要なら新規項目を起票する。
- 完了後のgit shell判定は、引用符外の`;`・改行・`&&`・`||`を各コマンドとして個別に行い、引用符内の区切りは引数として扱う。パイプ先は名前が完全一致する許可済み出力フィルタだけを通す。`sort -o/--output/--compress-program`（引用・短縮形の連結引数を含む）や空のパイプ・末尾の`&&/||`は停止する。`git pull`・`--force`・`--rebase`・`--abort`も停止する。引用された危険オプション・`--output`・外部diff/textconv・引用符の隣接連結・scriptblock・変数展開・未閉じ引用符・単独`&`・置換・`2>&1`以外のリダイレクト・未対応構文は停止する。これは完全なshell parserではないため、複雑な記法はToDoを`in_progress`にして実行する。
- shell入力は1回だけ解析し、確認・merge・非対応を共通分類して許可判定とレビュー判定で再利用する。
- Gitのコミット・確認工程では完了済みレビューを無効化しない。`merge`は作業ツリーを変更し得るので再レビューが必要。
- 公開状態とactive loadoutが変わらない操作では、宣言を再構築しない。再開・タスク開始時は強制的に再投影する。
- idle時の新しい外部入力でゲートをリセット（steer / followUp / 拡張入力では継続）。セッション開始・ツリー切替では最新の成功・有効なToDoスナップショットだけを逆順探索して復元し、失敗結果は無視する。`in_progress`が残っていればゲートは開いたままにする。
- モデルにツールを提示する前にJevが利用可能なら、依頼が起票に値するかをタスクごとに1回だけJevで判定する。質問・説明・単発の調査・単発の小さな作業など起票不要と明確に判断された場合は、そのタスクのゲートを解除する（起票は任意）。「OK」「続けて」のように前の会話に依存する依頼は作業の大きさが分からないため解除しない。判定が曖昧・起票必要、Jev未設定・無効、失敗・タイムアウト、ホスト未提供（拡張の単体利用）は従来どおり停止する。非同期判定の完了後も、現在の進行項目・並列呼び出しが消費した変更枠・中断状態を再確認する。steer / followUpで指示が追加されたら判定をやり直す。
- 停止理由はツール結果で即時通知する。終了前点検（`agent_before_settle`）が、未起票のまま停止した・未完了項目が残っている・変更系ツール使用後にレビューが未完了のタスクを検出すると、是正メッセージを加えて同じタスクを自動で継続させる（1タスク最大2回。超えたら終了を許可）。質問してユーザーの判断を待つ場合も未完了項目は是正対象になるため、その項目は`cancelled`にして理由を報告するか、先に`completed`にする。中断・エラー終了では発火しない。停止理由と是正メッセージは日本語で、UI・ログと表記を揃える。
- Jev免除は小さなタスク向けで、免除下の変更系が3回を超えると失効し、以後はJevを再判定せず従来どおり停止する。起票中は未完了ToDoが毎リクエストの末尾に`[ToDo状態]`として注入される（ユーザー指示ではなく状態表示。圧縮後も残る）。
- 起票後も更新を怠らない。完了した項目はその場で `completed`、次の項目を `in_progress` にし、まとめて更新しない。
- `todowrite`が非アクティブなら実行ゲートは無効。起票に値する作業は、ツール利用不能を報告して変更せず停止する。

## 違反パターン（自己診断）

- 前の会話の `pending` / `in_progress` ToDo に気づいたのに掃除せず新タスクを始めた
- 起票に値する作業なのに `todowrite` を 1 回も呼んでいない
- 起票不要と判断した作業が複数の依存する手順に膨らんだのに起票しなかった
- 変更後のレビューを省き、問題の修正・再レビュー前に最終完了工程へ進んだ
- 複数の `completed` 更新を最後に一括で行った
- 対応するToDoがまだ `pending` のまま「完了」と宣言した
- ターンを未完了 ToDo のまま終え、次の会話へ持ち越した
- ToDoを登録したタスクなのに`作業状況:` 行のない最終報告、またはToDo未登録のタスク（短い回答・起票不要の単発作業）に同形式を付けた
- 報告後の ToDo 更新（報告前に更新すべきだった）

## 回復手順

このターン内で上記違反が 1 つでも起きていた場合、続行する前に**今すぐ**
`todowrite` を 1 回呼んで実態と一致させ、以降の規則を守る。
